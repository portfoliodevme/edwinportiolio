Project overview

Explanatory

ODBRMS is a web-based backup and recovery management system for organisational data. It brings backup sources, storage destinations, schedules, restore jobs, integrity checks and audit records into one interface.

The system can protect two kinds of source: filesystem directories, which are stored as compressed ZIP archives, and MySQL/MariaDB databases, which are exported as SQL dumps and stored inside ZIP archives. Users can run backups manually or schedule them to run automatically.

The interface is served by Flask and uses HTML, CSS and JavaScript. The application stores its configuration and operational records in MySQL, while backup archives and restoration output are written to registered filesystem destinations.

Designed around trustworthy recovery

Every backup archive receives a SHA-256 checksum. Before restoring, the system re-verifies the archive and its incremental chain, validates archive paths, and refuses unsafe operations unless an administrator explicitly authorises them.

Problem statement

Explanatory

Organisations keep important records in folders and databases. Without a planned backup process, data can be lost through accidental deletion, hardware failure, corruption or other incidents. Manual backups are also easy to forget and difficult to prove.

A useful system must do more than copy files. It needs to schedule work, record what happened, prove that stored archives are intact, restore data safely, avoid deleting the last valid recovery point, and show who performed each action.

ODBRMS was built to address those needs in a single, auditable application.

What the system does

The main capabilities implemented in the project.

  • File and database backups

    Back up directories as streaming ZIP archives and MySQL databases as validated SQL dumps.

  • Full and incremental backups

    Filesystem sources support incremental backups with a protected parent chain back to a full base backup.

  • Scheduled protection

    Daily, weekly and monthly schedules run through APScheduler in a configured timezone.

  • Storage management

    Register local, secondary, removable or network destinations and monitor capacity and online status.

  • Integrity verification

    Recompute SHA-256 checksums to confirm that archives have not been corrupted or altered.

  • Safe recovery

    Restore files or databases into protected destinations with validation and explicit confirmation.

  • Retention rules

    Remove expired backups while protecting chains, active jobs, locked records and the newest recovery point.

  • Roles and audit trail

    Separate administrator, operator and viewer permissions while recording important actions.

  • Reports and analytics

    Review backup, storage, recovery and verification activity, with CSV export for selected reports.

Architecture

The application follows an application-factory pattern with separate route, service and model layers. Operations that take time run in background threads, and scheduled backups are managed by APScheduler.

Backend request flow

A route validates the request and delegates the work to a service. Services update SQLAlchemy models and write audit records. Long-running work is submitted to a thread pool with its own Flask application context.

Frontend request flow

Each page is a standalone HTML document. Shared JavaScript handles authentication, CSRF tokens, navigation, API calls, formatting and progress polling.

How a backup works

Explanatory
  1. 1

    Request and validate

    An operator selects a source, destination and backup type. The system checks permissions, source state, storage availability and whether another backup is already running.

  2. 2

    Queue the operation

    A backup record is created with a pending status and submitted to the background worker pool so the interface remains responsive.

  3. 3

    Collect the data

    For files, the engine enumerates regular files without following symbolic links. For databases, it runs a consistent MySQL dump using a temporary credentials file.

  4. 4

    Build the archive

    Data is streamed into a ZIP archive in chunks. A manifest records the source, backup type, file details and per-file SHA-256 hashes.

  5. 5

    Finalise safely

    The finished archive is hashed, moved into place atomically, recorded in the database and written alongside a manifest file. Failures clean up partial archives and are logged.

  6. 6

    Optionally verify

    If automatic verification is enabled, the system immediately queues a checksum check. Retention can also run after a scheduled backup completes.

Filesystem incremental backups compare each file's size and modification time against the cumulative chain index. Database backups are always full, so a database archive is never mislabelled as incremental.

Recovery and verification

Explanatory

Recovery is treated as a controlled operation rather than a simple file copy. The system checks the selected backup, verifies every archive in the chain, validates every archive entry, and only then writes restored data.

Checksum before restore
Each archive is re-hashed and compared with the checksum recorded at backup time. A mismatch aborts the operation before any data is written.
Chain integrity
An incremental backup cannot be restored without its full parent chain. The full chain is verified first.
Archive path safety
Entries are rejected if they contain absolute paths, parent-directory traversal, unsafe Windows path forms or symbolic links.
Atomic file writes
Restored files are written to temporary names and moved into place, reducing the risk of leaving partially written files.
Safe database targets
Database restores use validated target names. By default they go into a test database prefixed odbrms_restore_; overwriting a production database requires explicit administrator authorisation.
SQL dump validation
Dumps are rejected if they contain database-level statements such as DROP DATABASE or USE. After import, the table count is compared with the manifest.

Security and reliability

The project applies controls at several levels so that backup and recovery operations are both protected and auditable.

  • Session authentication with Flask-Login and hashed passwords.
  • Role-based access for administrators, operators and viewers.
  • Lockout after repeated failed sign-in attempts.
  • CSRF protection for state-changing API requests.
  • Security headers and no-store caching for API responses.
  • Configured allowlists for source, restore and destination paths.
  • Database passwords encrypted at rest with Fernet; credentials are not passed on command lines.
  • SHA-256 checksums for archives and per-file hashes in the manifest.
  • Atomic archive creation and temporary-file restoration.
  • Interrupted jobs are marked failed on restart instead of being reported as successful.
  • Retention protects the newest recovery point, active chains and records in use.
  • Every important action is written to the activity log with user, IP address and timestamp.

Running the project

ODBRMS is a Python application. It needs Python, MySQL or MariaDB, and the MySQL client tools used for database dump and restore.

  1. 1

    Clone the repository

    Download the project from GitHub and open a terminal in the project folder.

    git clone https://github.com/portfoliodevme/backup.git
cd backup
  2. 2

    Create a virtual environment

    Install the Python dependencies from the requirements file.

    python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
  3. 3

    Configure the environment

    Copy .env.example to .env and set the database URL, secret key, backup paths, allowed roots and MySQL tool paths.

  4. 4

    Prepare the database

    Create the MySQL database and apply the schema using migrations, or use the initialisation command on a fresh setup.

    set FLASK_APP=run.py
flask db upgrade

# Alternative for a fresh database:
flask init-db
  5. 5

    Create an administrator

    Use the built-in CLI command to create the first administrator account.

    flask create-admin
  6. 6

    Start the application

    Run the Flask entry point. The scheduler starts with the application by default.

    python run.py
  7. 7

    Check the tools

    Confirm that mysqldump and mysql are available at the configured paths.

    flask check-tools

The full setup, configuration and API details are documented in the repository's PROJECT_OVERVIEW.txt file and in the application configuration.

Scope and project notes

  • Incremental backups are supported for filesystem sources only; database backups are always full SQL dumps.
  • The default configuration is Windows/XAMPP-oriented, but the application is a cross-platform Flask project.
  • Background work uses an in-process thread pool rather than a separate distributed queue, so worker capacity should be planned for the deployment.
  • Only one scheduler process should run against a database to avoid duplicate automatic backups.
  • Restores are constrained to configured allowlist roots and safe database target names.
  • The project is intended for organisational backup management and academic demonstration, not as a replacement for a full enterprise backup platform.
