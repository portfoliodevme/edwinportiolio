IntelliDocs: AI Document Classification and Review System

A full-stack Flask and MySQL web application that reads uploaded documents, classifies them automatically, sends uncertain results to a human reviewer, and keeps a complete audit trail of every decision.

Project overview

Explanatory

IntelliDocs is a web application for organisations that receive large volumes of mixed paperwork. A person uploads a document, and the system reads it, decides which category it belongs to, and files it automatically when it is confident enough to do so.

When the model is not confident, the document is not silently filed. It is routed to a review queue where a reviewer reads the extracted text, sees the model's probabilities, and either confirms the suggestion or assigns the correct category. Every decision is recorded.

The application is served by Flask and uses server-rendered HTML templates with vanilla JavaScript on the front end. Configuration, documents, classifications, corrections and audit history live in MySQL, while the uploaded files and the trained model are stored on disk.

The model assists, a person decides

IntelliDocs does not treat a prediction as a verdict. A human reviewer remains accountable for the final category, corrections are captured as verified training data, and the production model is never retrained automatically behind the reviewer's back.

Problem statement

Explanatory

Organisations receive documents in many formats: scanned PDFs, Word files, plain text and photographs. Filing them by hand is slow, and doing it inconsistently makes searching, reporting and auditing difficult.

Automation alone is not the answer either. A classifier that confidently misfiles a legal contract as a payslip is worse than no classifier, and a system that cannot explain why a document was categorised cannot be trusted or audited.

A useful system therefore needs three things at once: reliable text extraction, a classification model that reports how confident it is, and a human review path for the cases the model is unsure about. IntelliDocs was built around that combination.

What the system does

The main capabilities implemented in the project.

  • Multi-format upload

    Accepts PDF, DOCX, TXT, PNG and JPEG files through a drag-and-drop queue with per-file progress, size checks and duplicate detection by SHA-256 hash.

  • Text extraction with OCR

    Reads embedded PDF text, Word paragraphs and tables, and plain text files. Scanned pages and images fall back to Tesseract OCR so they are not discarded.

  • Calibrated classification

    A TF-IDF plus calibrated Linear SVM model produces a prediction together with a real probability for every category, not just a label.

  • Human review queue

    Low-confidence predictions and failed extractions appear in a queue with the extracted text and full probability breakdown for a reviewer to resolve.

  • Category management

    Administrators manage the taxonomy, reassign documents between categories and are warned when a category is not supported by the deployed model.

  • Dashboard and analytics

    Charts show category distribution, monthly upload trends, processing outcomes and model quality, with a verified accuracy figure computed from real reviews.

  • CSV and PDF reports

    Administrators export the selected date range as a spreadsheet-ready CSV or a formatted PDF containing the metrics, the confusion matrix and per-category quality figures.

  • Audit trail

    Uploads, classifications, reviews, corrections, deletions, sign-ins and settings changes are all logged with the user, the action and the client address.

  • Three access roles

    Staff upload documents, reviewers resolve the queue, and administrators manage categories, settings, reports and deletions.

  • Feedback-driven retraining

    Reviewer corrections are stored as verified feedback and can be exported or used to retrain the model through a separate, deliberate command.

Architecture

The application follows an application-factory pattern with separate route, service and model layers, so that each concern can be tested and reasoned about on its own.

Backend request flow

A route validates the request and delegates the work to a service. Services coordinate the model, the storage layer and the database, and write an audit record for anything important. Each stage of processing fails independently, so an extraction error never leaves a half-classified document behind.

Frontend request flow

Each page is a standalone document rendered by Flask. A shared JavaScript service layer handles authentication, CSRF headers, uploads with progress, timeouts, error toasts and the formatting of dates, sizes and confidence scores.

The classification pipeline

Explanatory

The classifier is a text pipeline rather than a neural network. That choice keeps it fast to train, easy to inspect and small enough to ship as a single file, while still producing the calibrated probabilities the review workflow depends on.

Stages of the IntelliDocs classification pipeline
Stage What happens
NormaliseText is Unicode-normalised, control characters removed and whitespace collapsed, while numbers and identifiers are preserved so that references and totals stay readable to the model.
VectoriseA TF-IDF vectoriser converts the text into weighted unigram and bigram features, capped at 10,000 features, with sublinear term frequency and English stop words removed.
ClassifyA linear SVM separates the four document categories with balanced class weights, so a smaller category is not overwhelmed by a larger one.
CalibrateThe SVM is wrapped in a sigmoid calibration step. Without this, the raw decision score would not be a probability and the confidence thresholds would be meaningless.
ThresholdThe calibrated probability decides the outcome: auto-classify, flag for review, or require manual classification. The probability for every category is stored alongside the result.
RecordThe prediction, the confidence, the model version, the per-class probabilities and the reason for review are written to the database as an immutable classification record.

Training and evaluation

Training is a deliberate, repeatable command rather than something that happens on deployment. The dataset is validated first, then split with stratification so each category is represented in both halves, and the result is evaluated on data the model never saw.

Dataset validation
Labels outside the four supported categories are dropped, texts shorter than 20 characters are removed, exact duplicates are deleted, and a quality report records what was discarded and whether class imbalance remains.
Evaluation
Accuracy, macro and weighted precision, recall and F1, a full classification report and a confusion matrix are computed on the held-out test split and stored in the model metadata.
Safe deployment
The model and its metadata are written to temporary files and moved into place atomically, so an interrupted training run can never leave a half-written artifact in production.
Version tracking
Each trained model receives a new version number, and its metadata records the dataset name and checksum, the training configuration, the environment versions and the metrics that belong to that exact artifact.

A note on the headline accuracy

The bundled starter model scores perfectly on its hold-out test set, because that set comes from a synthetic starter corpus that is clearly labelled as such. The project states this openly in the model metadata, in the CLI output and in the dashboard banner. The figure is a working demonstration of the pipeline, not evidence of real-world accuracy. Real performance is measured from human-verified reviews, and the deployed model is meant to be retrained on the organisation's own labelled documents.

The human review loop

Explanatory

The thresholds are the heart of the design. They convert a raw probability into an operational decision, and they are adjustable by an administrator at runtime without a redeployment.

IntelliDocs confidence bands and the action taken in each
Band Confidence Action
Auto-classifiedAt or above 0.80Filed automatically under the predicted category and removed from the review queue.
Flagged, low confidence0.60 to 0.80Sent to the review queue so a reviewer verifies the prediction and confirms or corrects it.
Manual reviewBelow 0.60Sent to the review queue with a clear instruction to assign the category manually from the document content.
Failed processingNot applicableExtraction or classification errors also appear in the queue, so a document is never silently lost.

The thresholds are validated on save: the review threshold must be lower than the confidence threshold, and both must sit between 0.50 and 1.00.

What a reviewer sees and does

  1. 1.The queue lists each document with the model's category, the confidence score, the reason it was flagged and the upload date.
  2. 2.The workbench shows the preview or the extracted text alongside the probability for every category, so the reviewer judges the document rather than the number.
  3. 3.Confirming the prediction marks the classification as reviewed. Correcting it marks the classification as corrected and records the original label.
  4. 4.Every correction is stored as verified feedback, which becomes training data for a later, deliberate retraining command.

Corrections never retrain silently

A reviewer correcting a document does not change the model that is serving traffic. The correction is queued as verified feedback, and an administrator runs the separate retraining command when they are ready to deploy a new version. Classification history and feedback are preserved across a retrain.

Text extraction

Explanatory

Extraction is deliberately conservative. Each format is handled by the library that understands it best, and a document that cannot be read produces a clear error rather than an empty classification.

PDF
Embedded text is read with PyMuPDF. If the page has no usable text, the page is rendered at 200 DPI and passed through Tesseract OCR. The page count is checked against the configured limit before any work begins.
DOCX
Paragraphs and table cells are collected with python-docx. Table rows are joined with a separator so column structure survives into the text the model reads.
TXT
Encoding is detected by trying UTF-8 with BOM, UTF-16 and Latin-1 in turn. Files that turn out to contain binary data are rejected.
Images
PNG and JPEG files are opened with Pillow, converted to RGB and passed to Tesseract for OCR. Image classification is refused when OCR is switched off, rather than producing a misleading low-confidence result.
Minimum usable text
Anything under 20 characters is treated as unreadable. The document is sent to the review queue with the reason, so a human can still file it.

Data model

The MySQL tables separate the documents from the classifications applied to them, which is what allows a document to keep its full history.

Main IntelliDocs database tables
Table Purpose
usersAccounts, scrypt password hashes, roles and activation state.
categoriesThe document taxonomy, with a description and a flag showing whether the deployed model supports each category.
documentsUploaded files, their hash, extracted text, page and character counts, OCR flag, processing status and soft-delete marker.
classificationsEach prediction with its confidence, per-class probabilities, model version, review state, reviewer and notes.
feedbackVerified reviewer corrections, holding the original prediction and the corrected category for later retraining.
activity_logsThe audit trail of user and system actions, with the client address and timestamp.
system_settingsRuntime settings such as the confidence thresholds, upload policy and the active model version.

Documents are soft-deleted. The database record is retained so that the audit history stays intact, and the physical file is removed separately.

Security and reliability

The project applies controls at several levels so that documents and the decisions made about them are protected and traceable.

  • Session tokens are stored in HttpOnly cookies and are never written to localStorage, so a cross-site script cannot read them.
  • Double-submit CSRF protection on every state-changing request, with the token read from a cookie and sent as a header.
  • Passwords are hashed with scrypt, and the password change endpoint rejects reusing the current password.
  • Role-based access control with three roles, where an administrator implicitly holds every permission.
  • The client filename is never used for storage. Files are saved under a generated identifier, so a crafted name cannot influence the path on disk.
  • Uploads are written to a temporary directory, checked for size and signature, hashed, and only then moved into permanent storage.
  • Duplicate uploads are detected by SHA-256 content hash, and stored paths are verified to remain inside the upload root.
  • The declared MIME type of a file is confirmed against its actual signature before it is accepted.
  • Security headers are applied to every response: content type sniffing blocked, framing restricted to the same origin, a strict referrer policy and a restrictive permissions policy.
  • Authenticated pages and API responses are served with caching disabled, so document content is not kept in shared caches.
  • Upload size and page limits are enforced on the server, not only in the browser.
  • Every important action is written to the activity log with the user, the action, the document and the client address.

Testing

Project result

The application is covered by an automated test suite run with pytest. The suite uses an in-memory SQLite database and a testing configuration that disables OCR, so the tests run quickly and without needing MySQL or Tesseract installed.

Running the project

IntelliDocs is a Python application. It needs Python, MySQL, and Tesseract OCR if scanned documents and images are to be processed.

  1. 1

    Clone the repository

    Download the project from GitHub and open a terminal in the project folder.

    git clone https://github.com/portfoliodevme/document.git
cd document
  2. 2

    Create a virtual environment

    Install the Python dependencies from the requirements file.

    python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
  3. 3

    Configure the environment

    Copy .env.example to .env and set the database URL, the secret keys, the storage paths and the Tesseract executable path.

  4. 4

    Prepare the database

    Create the MySQL database, then initialise the tables, the default categories and the system settings.

    set FLASK_APP=app.py
flask init-db
  5. 5

    Create the first administrator

    Use the built-in CLI command to create the administrator account securely.

    flask create-admin
  6. 6

    Train and deploy the model

    Train the classifier from the starter dataset and deploy it. The command prints the version, the labels and the hold-out metrics.

    flask train-model
flask model-info
  7. 7

    Start the application

    Run the Flask entry point and open the application in the browser.

    python app.py
  8. 8

    Improve the model with real documents

    Once reviewers have corrected enough documents, export the verified corrections or retrain directly from them.

    flask export-feedback
flask retrain-from-feedback

The full configuration options, the API endpoints and the CLI commands are documented in the repository's .env.example file and in the application configuration.

Scope and project notes

  • The taxonomy is fixed to four categories, Academic, Administrative, Financial and Legal. Additional categories can be created in the interface, but a new category is not something the deployed model can predict until the model is retrained.
  • The bundled starter model is trained on a synthetic corpus, so its hold-out metrics describe that corpus and nothing else. Real accuracy is read from human-verified reviews.
  • Classification happens during the upload request rather than in a background queue, which keeps the implementation simple and gives the user an immediate result.
  • Processing is synchronous, so very large files will take longer to classify. The upload limit and page limit bound the worst case.
  • The MySQL configuration is aimed at a local XAMPP installation, but the application itself is a standard cross-platform Flask project.
  • OCR quality depends on the Tesseract installation and on the quality of the scan. Documents that OCR cannot read are sent to the review queue rather than discarded.
  • Corrections improve the model only when an administrator runs the retraining command. The production model is never changed as a side effect of a review.
  • The project is intended for document filing, review and demonstration, not as a replacement for a full enterprise records management platform.
